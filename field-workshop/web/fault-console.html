Change the shop's response

A timeout is how long Storefront waits for a dependency. A fallback provides a useful, honest response when that dependency fails or takes too long. A shorter timeout without a fallback can still produce an error.

Changes apply to new customer requests immediately. You do not need to restart Docker. Keep or reapply the same fault to compare the customer experience before and after mitigation.

Underlying API commands

These controls send HTTP requests to Toxiproxy. The Storefront uses the affected paths.

  • Apply delay: POST /proxies/{dependency}/toxics with a downstream latency toxic. An existing console delay is updated at POST /proxies/{dependency}/toxics/workshop-latency.
  • Remove delay: DELETE /proxies/{dependency}/toxics/workshop-latency.
  • Disconnect / reconnect: POST /proxies/{dependency} with {"enabled":false} or {"enabled":true}.
  • Clear all faults: POST /reset. Reconnects both paths and removes all toxics.
  • Refresh: GET /proxies. Reads state without changing it.

Example: 1500 ms Inventory delay

POST /proxies/inventory/toxics
Content-Type: application/json

{"name":"workshop-latency","type":"latency","stream":"downstream","attributes":{"latency":1500,"jitter":0}}

Fallback settings API

GET /api/mitigations reads current settings. POST /api/mitigations applies a dependency's timeout and fallback, or restores defaults. The console forwards these requests to Storefront's internal settings listener.
